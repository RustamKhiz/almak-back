# Пользователи и роли — этап R1

Состояние: код подготовлен локально; рабочая БД и аккаунты не изменены. Заданы логины: `almak` — admin, `manager1` и `manager2` — manager.

## Доступ

Обе роли имеют одинаковый полный доступ ко всем текущим функциям. Политика находится в `internal/models/user.go`, подключена к защищённым маршрутам через `RequirePermission`. В дальнейшем ограничения меняются на сервере; скрытие кнопки на клиенте не является проверкой права. Никаких отдельных ограничений менеджерам сейчас нет.

На каждом защищённом запросе проверяется существующий пользователь и актуальная роль из БД. Роль и логин из JWT не используются как источник прав. Удалённый пользователь не сохраняет доступ по старому токену. `GET /api/me` (также `/me`) возвращает ID, логин, имя, роль и список возможностей. Вход и refresh в вебе и Electron дополнительно возвращают поле `user` того же формата. Старые клиенты могут игнорировать новое поле.

Миграция добавляет роль manager существующим строкам. Точный существующий аккаунт получает admin отдельной командой по логину, без замены его ID или пароля. Старт приложения больше не создаёт встроенный аккаунт, не удаляет логин admin и не меняет пароли. На новой пустой БД первого администратора создаёт оператор командой ниже.

## Команда оператора

Сборка: `go build -o almak-users ./cmd/users` (на Windows указать имя с `.exe`). Запускать из каталога с серверным `.env`; значения DB_* и JWT_SECRET берутся обычным загрузчиком конфигурации. Команда мигрирует только таблицу пользователей, без миграций заказов.

- `almak-users -action grant-admin -login almak`: повышает существующий аккаунт, не создавая новый и не меняя пароль.
- `almak-users -action create -login manager1 -role manager`: пароль читается только из stdin, имя при необходимости через `-name`. Пароль не передавать аргументом командной строки. Для первого администратора пустой БД явно указать `-role admin`.
- `almak-users -action provision-team`: читает один JSON из stdin, назначает администратора и создаёт двух менеджеров в транзакции. Любая ошибка откатывает все изменения аккаунтов. Отсутствующий администратор не создаётся автоматически.

Контракт JSON для provision-team (пароли ниже — обозначения, не реальные значения):

```json
{
  "adminLogin": "almak",
  "managers": [
    { "login": "manager1", "name": "", "password": "<индивидуальный пароль>" },
    { "login": "manager2", "name": "", "password": "<другой индивидуальный пароль>" }
  ]
}
```

Минимум 12, максимум 72 байта, bcrypt. Повтор команды не меняет пароль уже существующего совпадающего аккаунта. Несовпадение роли/имени существующего менеджера — ошибка, а не молчаливая перезапись. Если аккаунт уже существовал, заново указанный пароль к нему не применяется: использовать исходные учётные данные. Не помещать реальные пароли в репозиторий, workflow inputs, аргументы процесса или логи.

## Настройка на сервере через Actions

1. После подтверждения публикации подготовить два индивидуальных пароля и передать пользователю через локальный защищённый файл. Сохранить исходный файл для первой выдачи; повторный запуск не является сменой паролей.
2. Записать JSON указанного формата в Actions secret `INITIAL_TEAM_ACCOUNTS` бэкенд-репозитория. Не подставлять пароль в текст shell-команды.
3. Опубликовать и развернуть бэкенд с R1. Затем вручную запустить `Provision initial users` из опубликованной ветки. Это отдельный workflow_dispatch, а не автоматическое создание пользователей при каждом деплое.
4. Workflow собирает административную команду и передаёт данные SSH через stdin. `scripts/provision_team.py` использует конфигурацию именно сервера; временная копия `.env` находится только на сервере в приватном каталоге и удаляется после завершения. Серверный `.env` не изменяется. Пароли и вывод ошибок команды не выводятся в Actions.
5. В результате показываются только ID, логины и роли. После успешной проверки трёх входов удалить временный secret `INITIAL_TEAM_ACCOUNTS`; повторная настройка возможна с тем же сохранённым JSON.
6. Проверить текущий вход almak без изменения пароля и вход manager1/manager2, `/me`, полный доступ к функциям, роль в меню, повторный запуск бэка. Потом публиковать фронт и обновление Electron с отображением профиля.

Не откатывать бэкенд на прежнюю версию, возвращающую сброс пароля при запуске. При экстренном откате сохранить исправление стартовой инициализации. Новые колонки совместимы со старой моделью, но старое поведение bootstrap небезопасно для новых настроенных аккаунтов.

## Проверки

`go test ./...`, `go vet ./...`, сборка `./cmd` и `./cmd/users`. Для интеграционных проверок задать `ALMAK_TEST_DATABASE_URL` в libpq key=value формате: отдельная PostgreSQL на loopback с именем БД `almak_test_*`. Тесты создают и удаляют только уникальные временные схемы внутри неё. Не использовать рабочую БД. CI поднимает отдельный PostgreSQL service.

Проверяются миграция прежней схемы пользователей, сохранение ID/хеша, повторная настройка, откат конфликтующей команды, оба способа входа и refresh, профиль обеих ролей, одинаковые права и чтение актуальной роли после изменения записи, отклонение удалённого пользователя/некорректного JWT subject.

R1 создаёт основу авторства; авторы будущих серверных черновиков и аудит изменений заказов добавляются в этапах D1/A1. Старые действия пользователям задним числом не приписываются.
